# 口試問答：被問到這個作品時怎麼回答

推甄口試的教授、面試官問作品，通常在確認三件事：**你懂不懂、你怎麼思考、你誠不誠實**。
下面每題都是「回答方向」，不是背誦稿。請先讀完 `導讀.md`，再用自己的話說，效果最好。

---

## 一分鐘介紹

> 我做了一個學日文的 App，叫 Hibi。一般背單字 App 的單字表是別人決定的，但我發現最容易記住的，是「今天自己想說卻說不出來」的話。
> 所以使用者只要用中文寫下今天發生的事，AI 就會挑出明天用得到的單字和句子；
> 複習時間則交給 FSRS 演算法，它用遺忘曲線估計每張卡「現在還記得的機率」，在快降到 90% 時才安排複習。
> 技術上，我把演算法和畫面分開，演算法部分用開源參考實作做對照測試，上萬個步驟結果完全一致。
> 目前的限制是還沒有真人使用資料，下一步想做的是用個人的複習紀錄訓練參數，並做校準分析。

---

## Q1. 間隔重複（spaced repetition）的原理是什麼？為什麼不每天複習？

- 記憶會隨時間衰退（遺忘曲線），但**在快忘記的時候成功想起來，記憶會被加強得最多**。
- 太早複習：還記得很清楚，效益低、浪費時間；太晚：已經忘了，要重新學。
- 所以最有效率的時機是「記得的機率快降到某個門檻」的時候。FSRS 把這個門檻叫目標記憶率，預設 90%。
- 可以舉導讀第 4 堂的例子：連續答對，間隔從 2 天 → 11 天 → 46 天。

## Q2. FSRS 和傳統的 SM-2 差在哪？為什麼選 FSRS？

- SM-2（1987）每張卡只記一個「容易度」，間隔用固定的乘法規則長大，**不會預測記得的機率**。
- FSRS 用三個量描述記憶：可提取率 R、穩定度 S、難度 D，可以預測「此刻記得的機率」，並依照目標記憶率反推間隔。
- FSRS 的參數是用大量真實複習紀錄訓練的，也可以用個人資料再訓練；Anki 從 23.10 版起內建 FSRS。
- 在開源的 srs-benchmark 上，FSRS 的預測誤差（log loss）明顯低於 SM-2。
- **可以補充的誠實說法**：SM-2 原本就不是設計來預測機率的，benchmark 是幫它加了公式才能比較，所以這個比較對 SM-2 不完全公平。

## Q3. 你怎麼確定演算法寫對了？⭐

- 公式寫錯一個符號，App 照樣能跑，只是排程悄悄變差，所以不能靠「看起來正常」。
- **對照測試**：用開源參考實作 ts-fsrs 當標準答案，隨機產生 2,000 組複習序列，每一步的 S、D 都要完全相等；
  為了逐位相等，連「每步四捨五入到小數 8 位」的細節都照做。
- **性質測試**：例如「經過 S 天後 R 剛好 90%」「目標記憶率越高間隔越短」「答對 S 一定變大」。
- 兩種測試互補：對照測試抓「跟標準不同」，性質測試抓「標準本身也可能錯」的情況。

## Q4. 怎麼評估這個系統有沒有用？⭐

- **演算法層面**：比較「預測記得的機率」和「實際有沒有記得」。App 的單字本頁已經有整體比較；
  更嚴謹的是把預測值分組畫**校準曲線**，或計算 **log loss**。
- **要誠實說的限制**：Demo 裡的資料是模擬的，而模擬學習者就是照 FSRS 的遺忘曲線產生的，
  所以「實際率接近預測」在模擬裡是必然結果，**不能當成證據**。要用真人資料。
- **學習成效層面**：可以設計小型使用者研究，例如兩週、每人同時有「AI 從日記挑的卡」和「隨機詞庫的卡」（受試者內設計），
  比較兩組卡在之後測驗的記得比例，以及使用者的採納率。

## Q5. AI 推薦的內容錯了怎麼辦？

- **格式錯**：程式不相信模型輸出——從文字挖出 JSON、逐欄驗證、壞的項目丟掉、讀音格式自動修正。
- **內容錯**（例如讀音錯）：內建詞庫有用 kuromoji 形態素分析器自動檢查讀音；
  同時發現分析器本身也會錯（例如把「十分」讀成「じゅうぶん」），所以採用「自動檢查＋人工確認白名單」。
  下一步可以把這個檢查用在 AI 產生的卡片上，有疑慮的標示出來。
- **使用者把關**：推薦結果要使用者勾選才加入，可以隨時編輯、刪除。

## Q6. 系統架構？為什麼這樣分？

- 三層：畫面（React Native）→ 平台能力（儲存、語音、字型）→ 核心邏輯（純 TypeScript）。
- 核心邏輯不依賴任何框架，所以能在 Node 上快速測試，未來搬到後端也不用改。
- AI 用 Provider 介面（策略模式），Gemini、Claude、離線示範三種實作可以互換，沒網路時自動退回離線。

## Q7. 資料存在哪？隱私和 API Key 安全怎麼處理？

- 資料只存在使用者裝置上（AsyncStorage），沒有後端。
- Gemini API Key 由使用者自己申請、只存在裝置、放在 HTTP header 而不是網址，備份檔也不會匯出金鑰。
- 這種「用戶端直接拿金鑰」只適合個人專案；正式上架應該改成經由自己的後端代理呼叫，金鑰不出現在 App 裡。

## Q8. 開發中遇到最困難的問題？

選一個你**實際重現過**的來講（見導讀第 9、10 堂的「動手」），例如：

- **網頁 Demo 整頁空白**：錯誤只有「Unexpected token '<'」。追查後發現 JavaScript 的 `String.replace` 會把替換字串裡的 `$'` 當成特殊符號，
  剛好 bundle 裡有這個字串，HTML 被插進程式碼中間。改成用函式當替換值就解決了。
  學到的是：**錯誤訊息指的位置不一定是原因所在**，要從「最近改了什麼」往回推。
- **讀音被截斷**：單元測試全過，但截圖一看讀音變成「ちゅ…」。原因是網頁版文字元件預設有 `max-width: 100%`。
  學到的是：**畫面問題要用截圖檢查**，所以後來把截圖變成端對端測試的一部分。
- **羅馬拼音的「は」**：一開始的規則在測試句上都對，但拿 kuromoji 逐句比對整個詞庫後，抓出「お釣りは」「締め切りは」這類
  送假名後面接助詞的句子念錯。學到的是：**自己想的例子通常只涵蓋自己想得到的情況**，要用獨立的參考答案大量比對。

## Q9. 如果再給你三個月，你會做什麼？

1. 找 10～20 位同學實際使用兩週，收集真實複習紀錄
2. 用個人資料訓練 FSRS 參數，比較訓練前後的 log loss
3. 做校準曲線，看模型在哪個區間高估或低估
4. 設計「日記推薦 vs. 隨機詞庫」的對照，評估推薦是否真的比較好記

## Q10. 這個作品跟你想讀的研究所方向有什麼關係？

依照你申請的實驗室調整，例如：

- **機器學習／資料科學**：FSRS 本質是用使用者紀錄訓練的機率模型，參數訓練、校準、log loss 都是 ML 的核心問題。
- **自然語言處理**：從中文日記抽取情境、生成適合程度的日文例句、自動檢查讀音，都是 NLP 問題。
- **人機互動／教育科技**：怎麼讓使用者願意每天寫、推薦怎麼呈現才會被採納，需要使用者研究。
- **軟體工程**：分層架構、對照測試、端對端測試、在受限環境（單一 HTML）部署。

## Q11. 這是你自己寫的嗎？有用 AI 嗎？⭐

**誠實回答，而且這可以是加分題。** 方向：

> 產品構想是我的：我想做一個能從自己生活中學日文的 App。實作上，我用 AI 程式工具（Claude）協作開發。
> 我的工作是定義需求、審查設計、驗證結果，並且讀懂每個模組。例如 FSRS 的公式、為什麼要做對照測試、
> 為什麼讀音格式這樣設計，我都可以說明；有些 bug 我也自己重現過。
> 我覺得現在的工程能力，有一部分是「知道怎麼讓 AI 產出可靠的東西」：要求測試、要求驗證、自己看懂再採用。

注意：
- **不要說「全部自己寫的」**。教授追問一個細節就會穿幫，信任一旦失去，整場口試都會受影響。
- 上面這段話要在你**真的讀完導讀、做過幾個動手練習**之後才說得出口，所以請先做功課。
- 被問到不懂的地方，直接說「這部分我還沒深入研究，我的理解是……」，比硬掰好得多。
