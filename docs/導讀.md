# 導讀：用零碎時間讀懂 Hibi

這份導讀分成 12 堂，每堂 10～20 分鐘，可以在通勤、下課空檔讀。
每堂都有「讀這些檔案」「重點」「想一想」，有空的話再做「動手」。

讀完、做過幾個動手練習之後，這個專案的每個設計你都講得出理由，面試或推甄口試被追問也不怕。

> 建議順序：第 0、1 堂先跑起來、看地圖；第 4～6 堂（FSRS）是最有學術含量、最常被問的部分，值得多花時間。

## 第 1 堂：專案地圖（10 分鐘）

**讀這些檔案**：`README.md` 的架構圖、`AGENTS.md`、資料夾結構

**重點**

程式分三層，依賴方向只能由上往下：

```
ui/、state/   畫面與狀態（React Native）
     ↓
platform/     裝置能力：儲存、語音、字型、claude.ai 偵測
     ↓
core/         純 TypeScript：演算法、資料格式、AI 解析
```

`core/` 不 import 任何 React Native 的東西，所以：
1. 可以直接在 Node 上用 Vitest 測試，跑完 117 個測試只要幾秒
2. 以後要做後端、做網頁版、換 UI 框架，核心邏輯都不用改

這就是「關注點分離」與「依賴反轉」：容易變的東西（畫面、平台）依賴穩定的東西（核心規則），反過來不行。

**想一想**
- 如果在 `core/scheduler.ts` 裡 `import { Platform } from 'react-native'`，會壞掉什麼？

## 第 2 堂：資料模型（10 分鐘）

**讀這些檔案**：`src/core/types.ts`

**重點**
- `Card`：一張卡。`ja` 是日文（含讀音標註），`meaning` 是中文，`srs` 是排程資訊。
- `SrsInfo`：卡片狀態（new／learning／review／relearning）、到期時間 `due`、記憶狀態 `memory`（S 與 D）。
- `ReviewLog`：每次複習的紀錄。特別注意 `predictedRecall`：**複習當下系統預測你記得的機率**。
  有了它，才能事後比較「預測 vs. 實際」——這是評估演算法準不準的關鍵（第 6、11 堂）。
- `Rating`：1 重來、2 困難、3 記得、4 簡單，和 Anki、FSRS 的定義相同。
- `Settings.profile`：首次設定選的程度、學習目的、興趣。`null` 代表還沒設定，App 會先顯示首次設定畫面。
  舊版資料只有 `learnerLevel` 一個欄位，讀取時由 `repo.ts` 的 `normalizeSettings()` 轉換——**改資料格式時，要想到使用者手機上的舊資料**。

**想一想**
- 為什麼要存每一次複習的紀錄，而不是只存卡片目前的狀態？（提示：重新訓練參數、統計、復原）

## 第 3 堂：讀音標註 `{漢字|かな}`（10 分鐘）

**讀這些檔案**：`src/core/ruby.ts`、`src/ui/components/RubyText.tsx`

**重點**
- 格式：`{勉強|べんきょう}する`，送假名放在括號外。
- 一份資料推導出三種形式：`toPlain`（純文字，用來去重、發音）、`toReading`（全假名，用來搜尋）、`parseRuby`（分段，用來排版）。
- React Native 沒有 HTML 的 `<ruby>`，所以 `RubyText` 自己排版：每個字是一個小直欄，上面讀音、下面本字，再用 `flex-wrap` 換行。
- 兩個細節：
  - **禁則處理**：「。」「、」「）」不能出現在行首，所以把它們黏在前一個字上（`toGroups`）。
  - **讀音外伸**：「注文」上面的「ちゅうもん」比兩個漢字寬。如果直接撐寬欄位，漢字前後會出現空隙；
    所以讓讀音先伸到左右「沒有讀音的字」上方（最多半個字），還不夠才撐寬。

**動手（15 分鐘）**
- 在 `ruby.test.ts` 加一個測試：`toReading('{東京|とうきょう}に{行|い}く')` 應該等於 `'とうきょうにいく'`，跑 `npm test`。

**延伸：羅馬拼音**（`src/core/romaji.ts`，選「零基礎」或「會五十音」時顯示）
- 假名換成羅馬字大多是查表，難的是**助詞**：「は」當助詞念 wa、在「はな（花）」裡念 ha，光看假名分不出來。
- 解法是利用讀音標註：`{今日|きょう}は` 的「は」緊接在一個有標註的詞後面，很可能是助詞。
  規則有例外（「お{釣|つ}りは」的「は」前面是送假名「り」），每個例外都寫在註解裡。
- 規則對不對，用 kuromoji 當參考答案：它會標出每個詞的詞性，詞性是「助詞」的「は」就換成「わ」，再整句比對（`romaji.test.ts`）。
  這跟第 6 堂的 FSRS 對照測試是同一個想法：**自己寫的輕量版本，用可靠但太大的參考實作來驗證**。

## 第 4 堂：FSRS 記憶模型（20 分鐘）⭐

**讀這些檔案**：`src/core/fsrs.ts`

**三個量**

| 符號 | 名稱 | 意思 |
| --- | --- | --- |
| R | 可提取率 retrievability | 此刻還記得的機率 |
| S | 穩定度 stability | R 從 100% 掉到 90% 需要的天數 |
| D | 難度 difficulty | 1～10，越難的卡，S 長得越慢 |

**遺忘曲線**（冪函數）：

R(t, S) = (1 + factor · t / S)^(−w₂₀)

`factor` 的取法讓 R(S, S) 剛好等於 0.9——這就是 S 的定義。用這個專案的程式算出來（S = 10 天）：

| 經過天數 | 1 | 5 | 10 | 30 | 100 |
| --- | --- | --- | --- | --- | --- |
| 還記得的機率 | 98.6% | 94.0% | 90.0% | 80.9% | 69.3% |

冪函數的尾巴比指數函數「長」：很久以前學的東西，忘得比指數模型預測的慢，這比較符合真實資料。

**下次間隔**：反解遺忘曲線，問「R 掉到目標記憶率 r 要幾天？」

| 目標記憶率（S = 10） | 80% | 85% | 90% | 95% |
| --- | --- | --- | --- | --- |
| 下次間隔 | 33 天 | 19 天 | 10 天 | 4 天 |

目標從 90% 提高到 95%，這張卡的間隔從 10 天縮成 4 天，複習頻率大約變成 2.5 倍。這就是設定頁說「調高會明顯變多」的原因。

**每次複習後怎麼更新**

- 第一次評分：S 直接查表。重來 0.21 天、困難 1.29 天、記得 2.31 天、簡單 8.30 天。
- 答對（困難／記得／簡單）：S 變大，而且
  - 越接近忘記才答對（R 越低），S 長越多 →「快忘記時複習效果最好」
  - D 越高（越難），S 長越少
  - S 已經很大的卡，成長倍率會遞減
- 忘記（重來）：S 掉回很小的值，D 變高。

一張卡連續評「記得」的實際數字：

```
新卡（當天兩個學習步驟都評記得）：S = 2.3 天 → 2 天後出現
2 天後 → 記得：S = 11.0 天 → 11 天後出現
11 天後 → 記得：S = 46.3 天 → 46 天後出現
（如果第三次評「重來」：S 掉到 1.5 天，D 從 2.1 升到 7.4）
```

**想一想**
- 為什麼「快忘記時複習」比「每天都複習」更有效率？用上面的公式解釋。
- D 為什麼要有「均值回歸」（`nextDifficulty` 裡的 w₇）？如果沒有，一張卡被評幾次「重來」之後會怎樣？

## 第 5 堂：排程策略（15 分鐘）

**讀這些檔案**：`src/core/scheduler.ts`、`src/core/time.ts`

**重點**
- **模型和策略分開**：`fsrs.ts` 只管「記憶狀態怎麼變」，`scheduler.ts` 決定「什麼時候出現」。這樣模型可以單獨驗證。
- **學習步驟**：新卡先在同一天內出現幾次（1 分鐘、10 分鐘），評「記得」走完步驟才「畢業」成複習卡，改用 FSRS 算出的天數。
- **一次算出四種結果**（`scheduleAll`）：按鈕上能預先顯示「1分／6分／10分／7天」，也能保證「困難 ≤ 記得 < 簡單」的間隔順序。
- **模糊化（fuzz）**：同一天學的 20 張卡如果間隔完全一樣，以後會永遠擠在同一天。加一點擾動（間隔越長、比例越小）讓複習量平均。
  用卡片 id 當亂數種子，同一張卡同一次複習永遠得到同樣結果——可重現、可測試。
- **學習日以凌晨 4 點分界**：大學生常熬夜，晚上 11 點和凌晨 1 點的複習應該算同一天。

**動手（20 分鐘）**
- 把 `makeConfig` 的 `learningSteps` 改成 `[1, 10, 60]`（多一個 1 小時的步驟），看 `scheduler.test.ts` 哪些測試失敗、為什麼。改回來。

## 第 6 堂：怎麼證明演算法寫對了（15 分鐘）⭐

**讀這些檔案**：`src/core/fsrs.test.ts`、`src/core/scheduler.test.ts`

**重點**

公式抄錯一個符號，App 照樣能跑，只是排程悄悄變差，肉眼看不出來。所以用兩種測試：

1. **對照測試（differential testing）**：用開源參考實作 ts-fsrs 當「標準答案」。
   隨機產生 2,000 組複習序列（評分分布模擬真實使用、間隔 0～200 天），每一步比對兩邊算出的 S 與 D，
   要求**完全相等**（不是「差不多」）。為了做到這點，連參考實作「每一步四捨五入到小數 8 位」的細節都照做。
2. **性質測試（property-based）**：不管輸入是什麼都該成立的數學性質，例如：
   - 經過 S 天後，R 剛好是 90%
   - 目標記憶率越高，間隔越短
   - 隔幾天後答對，S 一定變大；忘記，S 一定變小；D 永遠在 1～10

**想一想**
- 對照測試的弱點是什麼？（提示：如果參考實作本身錯了呢？所以還需要性質測試從另一個角度檢查。）

**動手（10 分鐘）**
- 把 `fsrs.ts` 裡 `nextRecallStability` 的 `(11 - d)` 故意改成 `(10 - d)`，跑 `npm test`，看對照測試怎麼抓到它。改回來。

## 第 7 堂：AI 層（15 分鐘）

**讀這些檔案**：`src/core/ai/provider.ts`、`prompts.ts`、`parse.ts`、`gemini.ts`

**重點**
- **Provider 介面（策略模式）**：畫面只呼叫 `suggest`／`chat`／`extractCards`，不知道背後是誰。
  三種實作：Gemini（使用者自備 API Key）、Claude（網頁 Demo 透過 claude.ai）、離線示範（內建詞庫）。
- **提示詞**：規定輸出 JSON，並給一個完整範例。範例比文字描述更能穩定輸出格式。
- **永遠不相信模型的輸出**（`parse.ts`）：
  - 從文字裡把 JSON 挖出來（模型常加 ```json 或說明文字）、容忍結尾多一個逗號
  - 每個欄位檢查型別與長度，壞掉的項目丟掉，不讓整批失敗
  - 讀音寫成 Anki 格式「漢字[かな]」時自動轉換
  - 程式端再去重一次，不只依賴提示詞裡的「不要重複」
- **錯誤訊息寫給使用者看**：HTTP 400 金鑰無效、429 額度用完、404 找不到模型、斷線，各自說明怎麼解決。
- **安全**：API Key 只存在裝置、備份不匯出、放在 HTTP header 而不是網址。
  正式上架應該改成「手機 → 自己的後端 → Gemini」，不把金鑰放在用戶端。

**想一想**
- 如果 AI 給的讀音是錯的，使用者會背到錯的東西。可以怎麼降低風險？（提示：第 8 堂的 kuromoji）

## 第 8 堂：從日記到推薦（10 分鐘）

**讀這些檔案**：`src/ui/screens/TodayScreen.tsx` 的 `suggest()`、`src/core/ai/demo.ts`、`src/core/data/`

**流程**
1. 收集輸入：日記、勾選的情境、學習者設定（程度、目的、興趣）、單字本已有的內容
2. 呼叫目前的 provider
3. 再過濾一次已經有的卡（`filterNew`）
4. 顯示「日記的日文版」與推薦清單，使用者勾選後加入

**學習者設定怎麼影響結果**（`src/core/profile.ts`）：
- 提示詞裡會寫「學生程度：會五十音」「學習目的：旅遊」「興趣：美食」（`learnerContext()`），初學者另外要求日記翻譯用簡單的です・ます體
- 新手包依學習目的挑情境：選「旅遊」會加入旅行、吃飯、便利商店（`starterTagsFor()`）
- 離線示範模式在日記裡找不到情境時，改用學習目的和興趣對應的情境；初學者會先挑 N5 的卡

**離線示範模式**：用關鍵字比對日記的情境（「便利商店」「打工」「睡過頭」…），從 116 項內建詞庫挑卡，
每種有配額（單字 4、句子 2、文法 1）。目的是讓沒有 API Key 的人（例如教授）也能走完整個流程。

**內建詞庫的品質檢查**（`starter.test.ts`）：讀音是人工輸入的，容易打錯。測試時用 kuromoji（日文形態素分析器）
自動算出每一句的讀音來比對。分析器也會錯——例如「十分遅れる」的「十分」它讀成「じゅうぶん（足夠）」，
實際是「じゅっぷん（十分鐘）」。這 15 處經人工確認後放進白名單，並寫下理由。
**自動化檢查 + 人工判斷**，兩者都需要。

## 第 9 堂：畫面與狀態（15 分鐘）

**讀這些檔案**：`App.tsx`、`src/state/store.ts`、`src/ui/screens/ReviewScreen.tsx`

**重點**
- **狀態管理**：沒有用 Redux，因為狀態不大。`store.ts` 用 React 內建的 `useSyncExternalStore` 加一個模組變數。
  每個動作：算新狀態 → 通知畫面 → 背景寫入儲存。畫面先更新，所以按鈕不會卡。
- **分頁**：四個畫面都保持掛載（切換時用 `display: none`），所以寫到一半的日記切回來還在。
- **復原**：評分前先記下舊的卡片狀態（`undo`），按「復原上一張」就換回去並刪掉那筆紀錄。
- **儲存**：手機是 AsyncStorage，網頁是 localStorage；外面再包一層 `SafeKV`，存取失敗時自動改用記憶體，App 不會打不開。

**一個真實的 bug**：網頁版用鍵盤複習時，評完一張馬上按空白鍵，偶爾會「沒反應」。
原因是 React 還沒重新繪製下一張卡，空白鍵的處理函式拿到的還是「已翻面的上一張」。
解法：不再用一個布林值記「有沒有翻面」，而是記「哪一張卡的第幾次複習已翻面」（`revealedKey`），換卡時自然就是未翻面。

## 第 10 堂：網頁 Demo 與端對端測試（10 分鐘）

**讀這些檔案**：`scripts/build-web-demo.mjs`、`scripts/smoke-web.mjs`

**重點**
- Expo 可以把同一份程式碼輸出成網頁。Demo 放在 claude.ai，頁面不能載入其他網址的程式，所以把 JS 內嵌成**單一 HTML 檔**。
- **端對端測試**：用無頭 Chrome 實際點過 11 個主要流程（示範資料、統計、複習、清空與首次設定、羅馬拼音、挑卡、問 AI、新增、設定、重新整理後資料仍在、深色模式），同時存下 README 用的截圖。

**兩個真實的 bug（都是端對端測試抓到的）**
1. **整頁空白**，錯誤訊息只有「Unexpected token '<'」。原因：`html.replace('</body>', 字串)` 的替換字串裡，
   `$'` 是特殊符號（代表「比對位置之後的文字」），而 JS bundle 裡剛好有 `$'`，於是 HTML 被插進 JS 中間。
   解法：替換值改成函式 `() => ...`，函式的回傳值不會被解析特殊符號。
2. **讀音被截斷成「ちゅ…」**。原因：網頁版的 Text 預設 `max-width: 100%`，絕對定位的讀音寬度被限制在漢字那一欄。
   這是看截圖才發現的，單元測試抓不到——這也是為什麼要截圖檢查畫面。

**動手（15 分鐘）**
- 把 `build-web-demo.mjs` 最後的 `() => ...` 改回直接傳字串，跑 `npm run demo:build && npm run demo:smoke`，親眼看它壞掉。改回來。
  （這樣你也有自己除錯的經驗可以講。）

## 第 11 堂：限制與下一步（10 分鐘）⭐

這一堂是推甄口試最好發揮的地方：知道自己的作品**哪裡還不夠**，而且知道**怎麼驗證**。

1. **參數個人化**：目前用 FSRS 預設參數（從大量 Anki 使用者訓練來的）。累積幾百次複習後，可以用自己的紀錄訓練參數：
   目標是讓 log loss（預測機率與實際結果的差距）變小。比較訓練前後的 log loss 就是一個小型實驗。
2. **校準分析（calibration）**：單字本頁的「實際 vs. 預測記憶率」是整體平均。更嚴謹的做法是把預測機率分組
   （例如 80～85%、85～90%……），每組比較實際記得的比例，畫成校準曲線。
3. **模擬不能當證據**：示範資料是用 FSRS 自己的遺忘曲線產生的，所以實際率接近預測是必然的。
   這是**循環論證**，要用真人資料才能評估。能主動說出這點，比宣稱「準確率 85%」更有說服力。
4. **推薦品質怎麼評估**：AI 挑的卡，使用者採納率多少？採納的卡跟隨機詞庫的卡相比，之後的記憶表現有沒有差別？
   這可以設計成一個小型使用者研究（例如兩週、受試者內設計）。
5. **工程面**：雲端同步與伺服器端 AI（Supabase 的資料表定義已經在 `supabase/`）、讀音自動檢查搬到後端、
   中翻日的「說出來」卡片、聽力卡。完整的階段規劃見 `docs/產品規劃.md`。
